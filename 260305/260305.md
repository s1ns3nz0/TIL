# 2. Domain Structure
## 1) Domain vs Bounded Context
### Domain
- Definition: Business problem area solved by software
- Subject: Business (Real world)
- Abstract: High(Conceptual)
- Relation: Multiple domain could exist in 1 domain
### Bounded Context
- Definition: Boundary of language/model where Domain model works
- Subject: Development Team(Architecture)
- Abstract: Low (Specific, presented by code)
- Relation: Unit of Domain Implementation 
## 2)  Domain(Buisness Problem): Buy Now, Pay Later Service
### Bounded Context(Credit): The specific model boundary which Credit team handle
- Core Domain: Credit <- This project
- Supporting Domain: Notification
- Supporting Domain: User/Identity
- Generic Domain: Payment Gateway

# 3. Code Description
## 1) Entitity is locked-in to Aggregate Root
- Entity is dependent on AR
- Only AR can create payment entity
```
# CreditAccount.make_payment()
@dataclass(eq=False)
class CreditAccount(BaseAggregateRoot):
    def make_payment(self, amount: Money, description: str = "") -> Payment:
        return payment
```
- Entity can't be accessed externally.
## 2) Value Object is an attribute of Entity/AR
```
# All CreditAccount fields are VO
class CreditAccount(BaseAggregateRoot):
    credit_score: CreditScore
    monthly_income: Money        
    credit_limit: CreditLimit      
    available_limit: Money 
```
## 3) Domain Event: Generated by AR, Collected by Application Service
- Domain Event is a messenger that connects the external world to the Aggregate Root.
```
# Inside of AR — Record the status change into events
def approve(self, limit):
    self.status = AccountStatus.ACTIVE
    self._record_event(CreditApproved(...))   # ← AR generates events

# Application Service — Collect and record events after AR saving them
self._repository.save(account)
for event in account.pull_events():          # ← App Service collects
    logger.info(event)                        # ← Recording (현재는 로깅)
```
## 4) Domain Service: Calculate the logics that AR can't do alone
```
# Application Service calls Domain Service
# Send the results to AR
approved, reason, limit = self._assessment_service.assess(
    credit_score, monthly_income
)
if approved:
    account.approve(limit)   # Apply results to AR
```
## 5) Repository - Search and save for AR
- Repository exists solely as an AR unit.
```
# Domain layer - Only Interface
class CreditAccountRepository(ABC):
    def save(self, account: CreditAccount): ...
    def find_by_id(self, id: str): ...
# Infrastructure layer - Specific Implementation
# No PaymentRepository, No StatementRepository, Only accessed via CreditAccount
class InMemoryCreditAccountRepository(CreditAccountRepository):
    _store: dict = {}
```
## 6) Application Service - Orchestrate Everything
- Application Service doesn't have business logic, only focuses on what to call and in what order?
```
Command (Input)
    → Repository로 AR 조회 / Search AR via Repository
    → Domain Service 호출 (필요시) / Call Domain Service (needed)
    → AR 메서드 호출 (비즈니스 로직 실행) / Call AR method (Excute business logic)
    → Repository로 AR 저장 / Save AR via Repository
    → Domain Event 수집/발행 / Collect and issue Domain Event
    → DTO 변환 후 반환 / Return DTO after conversion
```
