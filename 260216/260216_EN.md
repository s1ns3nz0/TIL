# 1. What is the Phoenix Server?
## 1.1 Definition
- A server management approach of deleting and recreating servers instead of fixing them when issues arise
## 1.2 Characteristics
### Immutability
- Servers never modified once created; when updates are required; existing servers are deleted and replaced with new ones reflecting the updates
### Reproducibility
- 코드로 관리되기 때문에 항상 똑같은 상태의 서버를 만들 수 있다.
- Because servers are managed as code, identical servers always can be created
### Short lifespan
- Regularry and irregularry deleting and recreating servers prevents unnecessary data accumulation.
## 1.3 Reasons for Adoption
- Prevents configuration drift: Prevents situations where services become available when servers are modified
- Security hardening: Removes attack artifacts and backdoors left by hackers
- Recovery automation: Automatically recovers using orchestration tools

# 2. DEV, Staging, Prod Zone Concepts
## 2.1 Definition
- Each stages before services are delivered to users
## 2.2 Description of Each Zone
- Dev(Development): Development environment where developers freely modify and test code
- Staging(QA): The environment most similar to production, where performance and integration tests are performed
- Prod(Production): The environment that users access

# 3. Multi-Account Strategy
In the past, multiple environments are seperated using tags and namepaces within a single account, but cloud-native approaches favor seperating environments into distinct accounts
## 3.1 Advantages
- Limit Blast Radius : Accidently deleting all resources in a Dev account doesn't affect services in prod accounts
- Security and Permission control: Dev account access can be granted to developers while blocking access to prod account
- Cost tracking: Seperate billing per environment enables clear budget management
- Quota management: Since each cloud service have resource creation limits, seperating accounts allows each account to have its own
## 3.2 Landing Zoneks
- A method of maintaing a dedicated account for shared services
- Shared Services Account: Manages shared tools management such as CI/CD tools, Image repositories
- Log Archive Account: Store logs from all accounts in one place
- Security Account: Guardrail configuration and integrated security monitoring 

# 4. Considerations for Capacity Planning in Cloud-Native Environments
## 4.1 Traffic Profile
- We must first understand how users access our services
    + Average TPS(Transactions Per Second): Number of requests to be processed per second under normal conditions
    + Peak Tiem load: Maximum traffic at specific times such as events and rush hours(Normally 3~5x average)
    + Concurrent users: Number of users maintaining active connections simultaneously
## 4.2 Resource Utilization
- Hardware usage must be measured when applications run
    + CPU vs Memory Intensity
        * CPU for compute-intensive tasks, Memory for caching and data processing
    + I/O Performance: Database read/write speed or network bandwidth limitations
    + Threshold configuration: CPU usage threshold is typically set to 60-70% rather than 100%
## 4.3 Load Testing
- Verifing actual limitations is more important than theoretical calculations
    + Stress Test: Identify the breaking point at which the systems fails
    + Breakpoint: Specific indicators; For example, Response speed exceeds one second when one instance processes 500 requests per second
    + Envrionment propagation: Testing in staging with the same specification as Prod increases reliability
## 4.4 Scaling Strategy
- Vertical Scaling(Scale-Up): Increasing server performance itself
- Horizontal Scaling(Scale-Out): Increasing the number of identical servers
- Auto Scaling 정책: 언제 서버를 늘릴 것인가? 최소/최대 개수는 얼마인가?
- Auto Scaling Policy: When should we increase the number of servers? What is the minimum/maximum counts?
## 4.5 Cost and Availibility Trade-Offs(SLO/SLA)
- Business requirements
    + Level of availability
    + Multi-Zone deployment

# 5. CMDB(Configuration Management Database)
- Flow of live state information
- Example of Coupang: https://www.theteams.kr/teams/8226/post/73235
## 5.1) Three Core Strategies for synchronizing with Actual Resources
### 5.1.1 Event-Driven Discovery
- Utilizes audit logs and event notifications provided by the cloud service provider
    + Mechanism: Updates CMDB when API call events such as resource creation and termination occurs
    + Advantages: Enables updating CMDB as soon as resources are created
### 5.1.2 Single Source of Truth based on IaC
- Leverage Iac Tools such as Terraform as an input source for CMDB
    + Mechanism: When code passes through the CI/CD pipeline, metadata of deployed resources is sent to the CMDB API
    + Advantages: Enables storing context of who, why, what codes are used to create the resource
### 5.1.3 Enforce Tagging as Trusted Indicators
- Leverages Tag information from cloud resources as key value for CMDB
    + Mechanism: A policy is applied that blocks creation or automatically delete resources without tags such as Service:Billing and Owner:DevOps_Team
    + Advantages: Enables logically grouping of tens of thousands of resources

# 6. Tag Policy
## 6.1) Why Tag Policies Are Necessary
- Cost Tracking
- Automation Targeting
- Security and Permission Control
## 6.2) Standard Tag Schema
- Name: web-asg-prod-01 / Resource identifier
- Environment: Dev, Staging, Prod / Categorization by zone
- Project: Phoenix-Migration / Belonging project or service
- Owner: devops-team, gildong.hong / Responsibility and contact information
- CostCenter: Dept-102, Margeting / Billing department categorization
- ManagedBy: Terraform, Ansible / Identifying infrastructure management tools

- Tagging should be enforced through policies
    + Blocking at creation: AWS Service Control Policies
- Post-creation detection and remediation: AWS Config
