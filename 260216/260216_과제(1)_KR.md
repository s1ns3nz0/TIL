# 1. 피닉스 서버(Pheonix Server)란 무엇인가?
## 1.1 정의
- 문제가 생기면 고치는 것이 아니라 삭제하고 새로 생성한다는 서버 관리 방식
## 1.2 특징
### 불변성
- 한 번 생성한 서버는 수정하지 않으며, 업데이트 등이 필요할 때는 기존 서버는 삭제하고 업데이트가 반영된 새로운 서버를 생성한다.
### 재현 가능성
- 코드로 관리되기 때문에 항상 똑같은 상태의 서버를 만들 수 있다.
### 짧은 수명
- 정기적/비정기적으로 서버를 삭제하고 생성하여 불필요한 데이터 축적을 방지한다
## 1.3 도입 이유
- 구성 드리프트 방지: 서버가 바뀌면 서비스가 되지 않는 현상 방지
- 보안 강화: 해커의 공격 흔적, 백도어 등을 삭제
- 복구 자동화: 오케스트레이션 도구에서 자동으로 복구

# 2. DEV, Staging, Prod 별 Zone 개념
## 2.1 정의
- 서비스가 사용자에게 제공되기까지의 각 단계
## 2.2 각 Zone별 설명
- Dev(Development): 개발 환경, 개발자가 코드를 자유롭게 수정하고 테스트
- Staging(QA): 실제 환경과 가장 유사한 환경이며 성능, 통합 테스트 수행 등을 수행
- Prod(Productinon): 실제 사용자가 접속하는 환경

# 3. Multi-Account(멀티 어카운트) 전략
과거에는 하나의 계정 안에 여러 환경을 넣고 태그(Tag)나 네임스페이스(Namespace)로 구분했지만, Cloud Natvie로 올수록 계정 자체를 분리하는 방식을 사용한다.
## 3.1 장점
- 폭발 반경(Blast Radius) 제한: Dev 계정에서 실수로 리소스를 다 삭제해도 Prod 계정 서비스는 영향이 없음
- 보안 및 권한 제어: 개발자에게 Dev 계정 권한은 주되, Prod 계정 접근은 차단 가능
- 비용 추적: 각 환경별로 청구서가 나오므로 예산 관리가 명확
- 쿼터(Quota) 관리: 클라우드 서비스마다 리소스 생성 제한이 있는데, 계정을 나누면 이 제한을 각각 가질 수 있음
## 3.2 랜딩존(Landing Zone)
- 공통 서비스용 계정을 따로 두는 방식
- Shared Services Account: CI/CD툴, 이미지 저장소(ECR) 등 공통 도구 관리
- Log Archive Account: 모든 계정의 로그를 한 곳에 모아 보관(보안 감사용)
- Security Account: 통합 보안 모니터링 및 가드레일 설정

# 4. Cloud Native 환경에서의 Capacity Planning 고려 요소
## 4.1 트래픽 패턴 분석(Traffic Profile)
- 우리 서비스에 사용자가 어떻게 들어오는 지 먼저 파악해야 한다.
    + 평균 TPS(Transactions Per Second): 평상 시 초당 처리해야 하는 요청 수
    + 피크 타임(Peak Time) 부하: 이벤트, 출퇴근 시간 등 특정 시점에 몰리는 최대 트래픽(보통 평균의 3~5배)
    + 동시 접속자 수: 실시간으로 연결을 유지해야 하는 사용자 수
## 4.2 리소스 사용량(Resource Utilization)
- 애플리케이션이 실행될 때 하드웨어를 얼마나 사용하는 지 측정해야 한다.
    + CPU vs Memory 집약도
        * 계산 작업이 많으면 CPU, 캐싱이나 데이터 처리가 많으면 Memory
    + I/O 성능: 데이터베이스 읽기/쓰기 속도나 네트워크 대역폭 제한 사항
    + 임계값(Threshold) 설정: 보통 CPU 사용률을 100%로 잡지 않고, 60~70% 정도를 적정 수준
## 4.3 부하 테스트(Load Testing)
- 이론적인 계산보다 중요한 것은 실제 한계치를 확인하는 것
    + Stress Test: 시스템이 어디까지 버티다 무너지는 지 확인
    + Breakpoint: '1개 인스턴스가 초당 500건의 요청을 처리할 때 응답 속도가 1초를 넘어선다.'같은 구체적인 지표
    + 환경 전파: 위에서 배포한 Staging 환경에서 운영(Prod)과 동일한 사양으로 테스트하여 신뢰도를 높입니다.
## 4.4 확장 전략(Scaling Strategy)
- Vertical Scaling(Scale-Up): 서버 자체의 성능을 올림
- Horizontal Scaling(Scale-Out): 동일한 서버의 개수를 늘림
- Auto Scaling 정책: 언제 서버를 늘릴 것인가? 최소/최대 개수는 얼마인가?
## 4.5 비용 및 가용성 타협(SLO/SLA)
- 비즈니스 요구사항
    + 가용성 수준
    + Multi-Zone 배포

# 5. CMDB(Configuration Management Database)
- 살아있는 상태 정보의 흐름
- 쿠팡: https://www.theteams.kr/teams/8226/post/73235
## 5.1) 실제 리소스와 싱크를 맞추는 3가지 핵심 전략
### 5.1.1 이벤트 기반 탐지(Event-Driven Discovery)
- 클라우드 사업자가 제공하는 감사 로그나 이벤트 알림을 활용한다.
    + 작동 방식: 리소스 생성, 삭제 등의 관련 API 호출 이벤트가 발생하면 CMDB에 업데이트
    + 장점: 리소스가 생성되자마자 바로 CMDB에 반영 가능
### 5.1.2 IaC 기반 Single Source of Truth
- Terraform같은 IaC 도구를 CMDB의 입력원으로 활용한다.
    + 작동 방식: 코드가 배포 파이프라인(CI/CD)를 통과할 때, 배포되는 리소스의 메타데이터를 CMDB API로 전송
    + 장점: 누가, 왜, 어떤 코드로 이 리소스를 생성했는 지 맥락까지 저장 가능
### 5.1.3 신뢰 지표로서 'Tagging' 강제화
- 클라우드 리소스의 Tag 정보를 CMDB의 키 값으로 활용
    + 작동 방식: Service:Billing, Owner:DevOps_Team 같은 태그가 없는 리소스는 생성을 차단하거나 자동 삭제하는 정책을 적용
    + 장점: 수만 개의 리소스를 논리적으로 그룹화 가능

# 6. Tag Policy
## 6.1) 태그 정책이 필수적인 이유
- 비용 추적
- 자동화 타겟팅
- 보안 및 권한 제어
## 6.2) 표준 태그 스키마
- Name: web-asg-prod-01 / 리소스의 식별 이름
- Environment: Dev, Staging, Prod / 어떤 Zone에 속하는 구분
- Project: Phoenix-Migration / 소속 프로젝트나 서비스 단위
- Owner: devops-team, gildong.hong / 책임 소재 및 연락처 확인
- CostCenter: Dept-102, Margeting / 비용 청구 부서 구분
- ManagedBy: Terraform, Ansible / 인프라 관리 도구 식별
## 6.3) 태그 정책의 강제화
- 정책을 통해 태그를 부착하는 것을 강제해야 한다.
    + 생성 시 차단: AWS Service Control Policies
- 사후 탐지 및 조치: AWS Config
